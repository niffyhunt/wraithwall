# Data policy — WraithWall Local Secure Sandbox

Scope: what may enter the sandbox, what must never enter it, what the
synthetic telemetry is, how it is marked, what may be exported, and what
reset/destroy do. [VERIFIED] statements describe Phase 4 code and are
test-enforced; [PROPOSAL] items are future scope and labeled as such.

---

## 1. What may enter the sandbox

| Data class | May enter? | Conditions |
|---|---|---|
| Synthetic seed data (repo-shipped, fixed-seed corpus) | Yes — default | Generated at `up` by `sb-seed`; LOCAL-marked at creation |
| HoneyFS bait content (repo-shipped generator) | Yes | Generated by the app's own `deception_rotator` into the sandbox volume |
| Startup canary seeds (`plant_canary_*`, honey tokens) | Yes | Obvious-fake conventions; created by normal app startup |
| Hostile strings (injection attempts) | Yes — as DATA | Corpus `INJECTION_STRINGS`; G12 property-tested; never executed anywhere |
| Real credentials, provider API keys, tokens | **Never** | Gate G9: credential-shaped env keys must be absent from generated config; verified dynamically per container |
| Production telemetry / customer data | **Never** | No host mounts (G3), no production network access, both planes internal (G7) |
| Live attacker traffic | **Never** | Nothing is published; no internet egress (canary on both planes); there is no listener reachable from outside the host |

The sandbox builds from an **allowlist build context** (H12): only repo source
needed by the app + the seed package is visible to the build. No `.env`, no
secrets, no host environment inheritance.

## 2. The synthetic telemetry

- **Generator**: `sandbox_kit/seed/` — deterministic (fixed-seed xorshift),
  stdlib-only, runs as the one-shot `sb-seed` container on the telemetry
  plane.
- **Corpus**: 24 sessions / 283 events / 24 binary ttylogs for `seed_version`
  "1". Session archetypes: recon, bait-reading (HoneyFS), credential-stuffing,
  hostile-string carriers, downloads/persistence.
- **Marking**: every record carries `"sandbox": "LOCAL"` and sensor
  `ww-sandbox-local`; tty output lines carry
  `[[WRAITHWALL-LOCAL-SYNTHETIC]]`. Container logs print the marker banner.
- **Determinism**: `corpus_digest` = SHA-256 over the exact byte stream. Same
  `seed_version` ⇒ identical bytes anywhere. The seed self-verifies the
  written file against the digest before shipping, and the launcher re-checks
  the receipt digest before RUNNING (E304 on mismatch).
- **Path**: `sb-seed` writes `synthetic.jsonl` + `tty/<sid>` into the shared
  in-project volume → the app's **own watcher** (`COWRIE_LOG_PATH`) ingests
  through the **unchanged** production pipeline → `cowrie_completed:*` +
  `cowrie_sessions:recent` → dashboards, SSE, MITRE, DNA, deception bus.
  The HMAC ship endpoint (`/api/v1/cowrie/ship`) is exercised as a wire
  protocol with a per-sandbox generated key (or clearly non-secret default).
- **Receipt**: `/state/synthetic/seed_receipt.json` records corpus digest,
  counts, ship results, and the marking note — the provenance artifact.

## 3. What stays local, by construction

- Both networks are `internal: true` with IP masquerade disabled; the egress
  canary runs on **both** planes at every start (E202 on any path).
- Nothing is published; the only route to the app is from the host across the
  internal bridge (management plane).
- The telemetry volume is the project's named volume — it exists only inside
  the sandbox project and is removed by `destroy`.
- The seed container has no egress, no docker socket, and cannot reach the
  host.

## 4. Export [PROPOSAL — Phase 5]

Not implemented in this release. `wraithwall sandbox export` remains an honest
stub. When implemented it must:

- include the seed receipt + corpus digest in every bundle,
- refuse to include anything not covered by the receipt,
- add the LOCAL banner to every exported artifact,
- require explicit interactive confirmation.

## 5. Retention, reset, destroy

| Operation | Effect on synthetic data |
|---|---|
| `stop` | Containers stop; the project volume (and corpus) is preserved |
| `reset` [Phase 5] | Removes the project volume; corpus + sessions + canary seeds regenerated at next `up` |
| `destroy` | Removes the project volume with the project — corpus, receipt, tty logs, seeded canaries all gone |

Because everything is regenerable from the fixed seed, no backup of sandbox
data is ever needed and no sandbox data has any retention obligation.

## 6. Provenance and evidence

- Every synthetic record is marked at creation (not at export) — marking
  cannot be forgotten downstream because it is part of the bytes.
- `sandbox_kit/seed/corpus.SEED_VERSION` is the provenance key; bumping it
  changes every digest and is a visible, greppable event.
- TTY replay output carries the LOCAL banner; `replay --list` prints sensor
  `ww-sandbox-local` per row.

## 7. Secure-deletion limitation

`destroy` removes files and the Docker volume, which unlinks the data.
It is **not** a cryptographic wipe: on SSDs/journaled filesystems, residue may
remain until overwritten. The sandbox never holds anything worth wiping
(synthetic data only, no secrets ever entered it) — this note exists so the
guarantee is stated honestly.
